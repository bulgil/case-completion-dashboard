# План по завершению

Локальный дашборд на Go для контроля плана завершений по Excel-выгрузкам.

## Запуск через Docker

Для сервера рекомендуется Docker Compose:

```bash
docker compose up -d --build
docker compose ps
```

Приложение доступно Caddy на `127.0.0.1:1987`. SQLite хранится в постоянном volume `completion-dashboard-data` и не удаляется при обычном `docker compose down`.

Если установлен [Task](https://taskfile.dev/), используйте короткие команды:

```bash
task up       # собрать и запустить
task logs     # открыть логи
task status   # проверить контейнер и healthcheck
task migrate-data # один раз перенести существующий ./data в Docker volume
task update   # git pull origin main и пересборка
task down     # остановить без удаления данных
```

Не запускайте `docker compose down -v`, если хотите сохранить загруженный план и SQLite.

При переходе с systemd на Docker сначала перенесите существующую базу и освободите порт:

```bash
task migrate-data
sudo systemctl disable --now case-dashboard
task up
```

## Запуск

```powershell
go run .
```

Через настроенный Caddy откройте `https://ВАШ-ДОМЕН/dashboards/completion-plan`, выберите месяц и загрузите `.xlsx`.

Первая загрузка ставит строки отчёта на постоянное отслеживание и фиксирует исходные дату СЗ и стадию сделки. Новые загрузки добавляют новые ID, не удаляя уже отслеживаемые. Контакт сопоставляется по `Контакт: ID`, сделка — по колонке `ID`.

Данные хранятся локально в SQLite `data/dashboard.db`. При первом запуске существующий `data/dashboard.json` автоматически переносится в SQLite. Путь можно изменить переменной `DATA_FILE`. Приложение всегда слушает порт `1987`, внешний URI приложения зафиксирован как `/dashboards/completion-plan`.

## Подключение как локальное приложение Bitrix24

Приложение предоставляет обработчик:

```text
https://ВАШ-ПУБЛИЧНЫЙ-ДОМЕН/dashboards/completion-plan
```

В Bitrix24 откройте **Разработчикам → Другое → Локальное приложение** и создайте серверное приложение с пользовательским интерфейсом:

- `Путь вашего обработчика` — URL выше;
- `Путь для первоначальной установки` — оставить пустым;
- `Использует только API` — выключено;
- права REST: `CRM` (чтение контактов).

Приложение раз в час в фоне обновляет контакт и сделку через Bitrix24 REST. Текущий статус контакта и дата СЗ используются для прежних счётчиков, а в таблице показываются зафиксированная и текущая стадии сделки. Кнопка «Обновить из Bitrix24» запускает тот же серверный цикл вручную.

Для фоновых запросов создайте в Bitrix24 входящий webhook с правами CRM, скопируйте `.env.example` в `.env` и укажите `BITRIX_WEBHOOK_URL`. Это секрет: не публикуйте URL и не добавляйте `.env` в Git.

Поля контакта зафиксированы в коде:

- `UF_CRM_1708427400582` — статус;
- `UF_CRM_1708427240655` — СЗ завершение.

Облачный Bitrix24 открывает обработчик во фрейме, поэтому URL должен быть доступен из интернета по HTTPS. `http://localhost:1987` для постоянной работы не подходит; используйте HTTPS reverse proxy на сервере или защищённый туннель для разработки.

Проверка доступности сервиса: `GET /dashboards/completion-plan/healthz` возвращает `ok`.

Для Caddy с `handle_path /dashboards/*` запустите сервис так:

```bash
DATA_FILE=/opt/case-completion-dashboard/data/dashboard.db ./dashboard
```

Префикс `/dashboards` остаётся общей точкой для будущих дашбордов. Это приложение использует slug `/completion-plan`. Основной маршрут принимает `GET` для обычного открытия и `POST` от Bitrix24. После удаления общего префикса Caddy передаёт приложению пути `/completion-plan`, `/completion-plan/static/style.css` и `/completion-plan/upload`. `/completion-plan/bitrix/app` сохранён как совместимый алиас.

# Case Completion Dashboard

Локальное приложение Bitrix24 на **Go** для сравнения исходного Excel-плана с актуальными данными контактов и сделок CRM.

Рабочий адрес: <https://pravv-dev.ru/dashboards/completion-plan>

## Как работает дашборд

1. Пользователь открывает локальное приложение внутри Bitrix24 и загружает `.xlsx`.
2. Сервер читает видимые строки первого листа. Скрытые строки, в том числе скрытые сохранённым фильтром Excel, пропускаются.
3. Значения из Excel фиксируются как состояние на начало периода.
4. После загрузки браузер пакетно получает актуальные контакты и сделки через JS SDK Bitrix24.
5. Статус контакта `UF_CRM_1708427400582` считается завершённым только при значении `Завершен успешно` (регистр, пробелы и `е/ё` нормализуются).
6. Текущая дата СЗ из `UF_CRM_1708427240655` сравнивается с исходной датой. Отличие увеличивает счётчик переносов.
7. В таблице выводятся исходная и текущая стадии сделки, исходный и текущий статусы контакта, а также поля ОКК.
8. Если в Excel нет колонки статуса контакта, исходный статус остаётся пустым и считается незавершённым.
9. Если в Excel нет ID сделки, приложение ищет сделку по Contact ID только в воронке «Завершение процедуры» (`CATEGORY_ID = 7`). Если найдено несколько, используется сделка с наибольшим ID.

Приложение не использует БД, не хранит загруженный отчёт и не выполняет фоновое отслеживание. После перезагрузки страницы файл требуется загрузить снова. Экспорт создаёт `.xlsx` из текущего отфильтрованного состояния таблицы.

## Стек и обязательные ограничения

- Язык backend: **Go**. Новую серверную логику также следует писать на Go.
- Версия Go задаётся в [`go.mod`](go.mod) и Dockerfile; сейчас это Go 1.26.
- HTML/CSS/JavaScript встроены в бинарник через `embed`.
- Развёртывание: Docker Compose за reverse proxy Caddy.
- Приложение слушает порт `1987`.
- Внешний base path: `/dashboards/completion-plan`.
- Внутренний путь приложения после `handle_path` Caddy: `/completion-plan`.

## Excel-файл

Поддерживается `.xlsx` размером до 25 MiB. Обрабатывается первый лист.

Обязательные колонки:

- `Название`
- `Контакт: Номер дела`
- `Контакт: Арбитражный управляющий`
- `Контакт: СЗ завершение`
- `Стадия сделки`
- `Контакт: ID`

Необязательные колонки:

- `Контакт: Статус`
- ID сделки (если отсутствует, применяется поиск в воронке 7)

## Интеграция с Bitrix24

### Настройка локального приложения

В Bitrix24 создайте локальное приложение с пользовательским интерфейсом и укажите обработчик:

```text
https://pravv-dev.ru/dashboards/completion-plan
```

Обработчик принимает и `GET`, и `POST`, поскольку Bitrix24 может открывать приложение POST-запросом. Приложению необходимо предоставить право **CRM**.

### Webhook и REST-доступ

Отдельный входящий или исходящий webhook **не требуется**. Авторизация выполняется JS SDK локального приложения (`BX24.init`), а запросы идут от имени открывшего приложение пользователя. Не добавляйте webhook URL или токен в исходный код.

Необходимые REST-методы Bitrix24:

- `crm.item.fields` — метаданные пользовательских полей контакта;
- `crm.item.get` с `entityTypeId: 3` — получение контакта;
- `crm.item.get` с `entityTypeId: 2` — получение сделки, когда её ID есть в Excel;
- `crm.deal.list` — поиск сделки по `CONTACT_ID` и `CATEGORY_ID = 7`, когда ID сделки отсутствует;
- `crm.status.list` — преобразование ID стадии сделки в название.

Используемые поля контакта:

| Поле | Назначение |
|---|---|
| `UF_CRM_1708427400582` | Статус контакта |
| `UF_CRM_1708427240655` | СЗ завершение |
| `UF_CRM_1786950686867` | Запрос суда проверен ОКК |
| `UF_CRM_1786950695618` | Отчёт проверен ОКК |

Пользователь Bitrix24 должен иметь права чтения соответствующих контактов, сделок, стадий и пользовательских полей. При отсутствии прав часть строк не обновится.

## Локальный запуск

Требуются Docker, Docker Compose и Task. Запуск:

```bash
task up
task logs
```

Проверки:

```bash
task test
task status
```

Локальная страница: <http://localhost:1987/completion-plan>. При прямом открытии вне iframe Bitrix24 REST-синхронизация недоступна, но загрузку и разбор Excel проверить можно.

## Reverse proxy Caddy

На сервере используется удаление внешнего префикса перед проксированием:

```caddyfile
handle_path /dashboards/* {
    reverse_proxy localhost:1987
}
```

Поэтому HTML-формы используют внешний base path `/dashboards/completion-plan`, а Go-маршруты обслуживают внутренний `/completion-plan`.

## Удалённый сервер и деплой

Подключение:

```bash
ssh root@pravv-dev.ru
```

Каталог проекта:

```text
/opt/projects/go-projects/case-completion-dashboard
```

Репозиторий: `https://github.com/bulgil/case-completion-dashboard.git`. Основная ветка для сервера: `main`.

Стандартный деплой:

```bash
ssh root@pravv-dev.ru
cd /opt/projects/go-projects/case-completion-dashboard
git pull --ff-only origin main
docker compose up -d --build --force-recreate
docker compose ps
docker compose exec -T completion-dashboard wget -qO- http://127.0.0.1:1987/completion-plan/healthz
```

Ожидаемый ответ healthcheck: `ok`.

Логи и диагностика:

```bash
cd /opt/projects/go-projects/case-completion-dashboard
docker compose logs --tail=200 completion-dashboard
docker compose ps
```

Dockerfile запускает `go test ./...` на стадии сборки. Если тесты не проходят, новый образ не создаётся и контейнер не следует считать успешно обновлённым.

## Команды Taskfile

```bash
task test      # Go-тесты
task build     # сборка образа
task up        # сборка и запуск
task rebuild   # чистая пересборка
task logs      # логи
task status    # контейнер и healthcheck
task update    # git pull main и запуск
```

## Безопасность

- Не коммитьте webhook-токены, OAuth-токены, cookies и `.env`.
- Не меняйте серверные файлы вне каталога проекта при деплое.
- Не удаляйте чужие локальные изменения без отдельного согласования.
- Перед деплоем фиксируйте изменения в Git и отправляйте их в `main`.

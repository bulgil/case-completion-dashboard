# Руководство по разработке дашбордов Bitrix24

Этот документ содержит общие правила создания и развёртывания новых дашбордов. Он не описывает бизнес-логику какого-либо конкретного дашборда.

## Основные принципы

- Каждый дашборд — самостоятельный проект на **Go**.
- Каждый дашборд — отдельное локальное приложение Bitrix24.
- Каждый проект имеет собственные исходники, Git-репозиторий, Docker-образ, контейнер, порт, URL и healthcheck.
- Проекты не следует размещать внутри каталога другого дашборда.
- Бизнес-логика, CRM-поля, Excel-формат и REST-методы определяются отдельно для каждого нового дашборда.

## Структура на удалённом сервере

Сервер:

```text
root@pravv-dev.ru
```

Все проекты дашбордов создаются отдельными каталогами внутри:

```text
/opt/projects/go-projects/
```

Пример:

```text
/opt/projects/go-projects/sales-dashboard/
/opt/projects/go-projects/court-dashboard/
/opt/projects/go-projects/quality-dashboard/
```

Для нового дашборда нужно придумать уникальное короткое имя в `kebab-case`. Нельзя использовать каталог существующего проекта, если пользователь не просит изменить именно этот проект.

## Технологический стандарт

Backend каждого дашборда должен быть написан на Go.

Рекомендуемая структура:

```text
dashboard-name/
├── main.go
├── go.mod
├── templates/
├── static/
├── Dockerfile
├── compose.yaml
├── Taskfile.yml
├── README.md
├── AGENTS.md
└── .gitignore
```

Обязательные требования:

- HTTP-сервер и серверная логика реализуются на Go;
- HTML, CSS и JavaScript можно встраивать в бинарник через `embed`;
- конфигурация запуска оформляется через Docker Compose;
- контейнер должен иметь healthcheck;
- порт и base path должны быть уникальны;
- секреты, токены и cookies не коммитятся;
- перед деплоем выполняются `gofmt` и `go test ./...`;
- Dockerfile должен запускать тесты на стадии сборки.

## Создание нового проекта

Для каждого нового дашборда:

1. Уточнить назначение, входные данные, показатели, таблицы и фильтры.
2. Придумать уникальное имя проекта и GitHub-репозитория.
3. Проверить на сервере, что каталог, порт и URL ещё не заняты.
4. Создать новый локальный каталог проекта, не изменяя существующие дашборды.
5. Реализовать приложение на Go и покрыть ключевую логику тестами.
6. Создать отдельный публичный или приватный GitHub-репозиторий по требованию пользователя.
7. Создать на сервере отдельный каталог `/opt/projects/go-projects/<project-name>`.
8. Настроить отдельный Docker Compose service и контейнер.
9. Добавить отдельный маршрут Caddy.
10. Создать отдельное локальное приложение в Bitrix24 и указать его URL обработчика.
11. Проверить приложение внутри iframe Bitrix24.

## Bitrix24: локальные приложения

Каждый дашборд регистрируется в Bitrix24 как отдельное локальное приложение с пользовательским интерфейсом.

Для каждого приложения нужны:

- собственное понятное название;
- отдельный URL обработчика;
- только необходимые права REST;
- обработка как `GET`, так и `POST`, поскольку Bitrix24 может открывать приложение POST-запросом;
- поддержка работы внутри iframe;
- корректный `Content-Security-Policy` для доменов Bitrix24;
- инициализация через `BX24.init` перед REST-вызовами;
- изменение размера iframe через `BX24.resizeWindow`, если это требуется интерфейсу.

Типовой внешний URL:

```text
https://pravv-dev.ru/dashboards/<dashboard-slug>
```

Значение `<dashboard-slug>` должно быть уникальным для каждого приложения.

## Webhook и REST

Для интерактивного локального приложения отдельный входящий webhook обычно не нужен: frontend использует JS SDK Bitrix24 и выполняет REST-запросы в контексте пользователя через `BX24.callMethod` или `BX24.callBatch`.

Не существует одного общего webhook для всех дашбордов. Для каждого нового проекта нужно отдельно определить:

- какие сущности Bitrix24 используются;
- какие REST-права нужны приложению;
- какие REST-методы вызываются;
- какие пользовательские поля используются;
- нужны ли фоновые серверные запросы или обработка событий.

Входящий webhook или OAuth на сервере требуется только тогда, когда дашборд должен обращаться к Bitrix24 без открытого iframe и без активной пользовательской сессии. Исходящий webhook или подписка на события требуется только для событийной интеграции. Если webhook действительно нужен:

- создавайте отдельный webhook для конкретного приложения;
- выдавайте минимальный набор прав;
- храните URL и токен в `.env` на сервере;
- добавляйте `.env` в `.gitignore`;
- никогда не записывайте секрет в README, AGENTS.md, исходный код или Git;
- документируйте только имена переменных окружения и процедуру настройки.

Конкретные методы и поля Bitrix24 фиксируются в README самого нового проекта после согласования требований.

## Порты и Caddy

Перед выбором порта нужно проверить занятые порты и существующие Compose-проекты на сервере. Нельзя копировать порт другого дашборда.

Для каждого приложения создаётся отдельный маршрут Caddy, например:

```caddyfile
handle_path /dashboards/example-dashboard/* {
    reverse_proxy localhost:UNIQUE_PORT
}
```

Нужно согласовать поведение `handle`/`handle_path` с маршрутами Go-приложения. URL форм, статики, загрузки и экспорта должны учитывать внешний base path.

## GitHub

Каждый новый дашборд должен находиться в отдельном GitHub-репозитории владельца `bulgil`, если пользователь не указал другое место.

Рекомендуемый порядок:

```bash
git init
git add .
git commit -m "feat: initialize dashboard"
git branch -M main
git remote add origin git@github.com:bulgil/<repository-name>.git
git push -u origin main
```

Создание репозитория и публикация кода выполняются только в рамках запроса пользователя. Не добавляйте в коммит файлы других проектов.

## Универсальная схема деплоя

Подключение к серверу:

```bash
ssh root@pravv-dev.ru
```

Первичное развёртывание нового проекта:

```bash
cd /opt/projects/go-projects
git clone git@github.com:bulgil/<repository-name>.git <project-name>
cd <project-name>
docker compose up -d --build
docker compose ps
```

Обновление существующего проекта:

```bash
ssh root@pravv-dev.ru
cd /opt/projects/go-projects/<project-name>
git pull --ff-only origin main
docker compose up -d --build --force-recreate
docker compose ps
```

После запуска необходимо проверить индивидуальный healthcheck приложения и публичный HTTPS URL.

## Проверка перед завершением работы

- проект находится в отдельном каталоге;
- приложение написано на Go;
- Git-репозиторий относится только к этому дашборду;
- порт, имя контейнера и Caddy path уникальны;
- локальное приложение Bitrix24 имеет отдельный обработчик;
- выданы только необходимые права REST;
- секреты находятся только в серверном `.env`;
- тесты проходят;
- Docker-контейнер healthy;
- публичный URL открывается;
- REST-запросы работают именно внутри Bitrix24.
